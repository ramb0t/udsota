# Changelog

All notable changes to udsota. Versions follow semantic versioning; the wire protocol is part of the public API.

## [Unreleased]

- **Breaking**, host builds: each component's sources move into `server/` (the generic UDS server and its transport), `update/` (the firmware updater) and `bootloop/` (the boot-loop breaker), and a new `sources.cmake` in `components/udsota` and `components/udsota_esp32` exports their file lists and include dirs. A host build that names udsota's files, such as an integrator's unit tests, `include()`s both files and takes their variables instead: `UDSOTA_SRCS`, `UDSOTA_INCLUDE_DIRS` and `UDSOTA_PRIV_INCLUDE_DIRS` (empty, kept so existing lists still expand) for the whole core, or a unit's list, such as `UDSOTA_SERVICES_SRCS` for what was `udsota_server.c` and `udsota_codec.c`, `UDSOTA_IMAGE_SRCS`, `UDSOTA_ESP32_INCLUDE_DIRS`, which gains `update/include`, and `UDSOTA_ESP32_PRIV_INCLUDE_DIRS`, which gains `server/priv` (a host build that compiles `bootloop/udsota_esp32_bootloop.c` needs both). `UDSOTA_COMPRESSION` is now read by `update/udsota_update.c`, not `udsota_server.c`, so a build that defines it for one file must move it. ESP-IDF builds and the wire are unchanged; the header changes are below. The host build now stops at configure time if a component holds a `.c` file its `sources.cmake` does not list or lists under another directory's list, or if `sources.cmake` names an include dir that doesn't exist, as ESP-IDF does.
- **Breaking**, core: the firmware updater's state moves out of `udsota_server_t` into its new `update` member (`udsota_update_t`), so code that read `srv.download_active`, `srv.last_dl`, `srv.dl_announced` or another download, slot or engine field reads `srv.update.*`. The server's own fields keep their names.
- **Breaking**, core: `udsota_priv.h` becomes `udsota_service.h`, in `server/include`. `udsota_isotp.h` and `udsota_service.h` include `udsota_server.h` where `udsota_isotp.h` and `udsota_priv.h` included `udsota.h`, so code that took `udsota_init`, `udsota_progress` or the updater's wire constants (F189/F1F0/F1F1/F1F3, the RIDs, the DFIs) from them includes `udsota.h` itself; the engine and progress types still come through. The headers split into the server's (`udsota_server_wire.h`, `udsota_server.h`) and the updater's (`udsota_update_state.h`, `udsota_update_wire.h`, `udsota_update.h`); `udsota.h` and `udsota_wire.h` include them all, so code that includes those is unchanged. `UDSOTA_DL_MAX_BLOCK_LEN` stays in the server's wire header: the core caps `cfg.max_block_len` with it and the transport sizes its receive buffer from it.
- **Breaking**, core: `udsota_init` with a NULL engine serves no update service: 34, 36 and 37 answer 0x11, and F189, F1F0, F1F1, F1F3, FF01 and F000-F002 go to the app's `did_read` and `routine`. Before, it crashed at 10 02, 11 01 or F002 and gave fixed answers elsewhere. With an engine nothing changes on the wire.
- Core: the server and the updater are split behind a one-way seam. The core's `server/` never calls the updater or touches its state; the one exception is that the server context embeds the updater's state type, `udsota_update_t` from `update/include/udsota_update_state.h` (116 B on ESP32), so a server-only build still needs that include dir. The updater registers as the server's one service through `udsota_service.h` (the `udsota_service_t` table and `udsota_register_service`). `udsota_core_init(s, cfg, security, hooks)` starts the server alone, `udsota_update_init(s, engine)` registers the updater on it, and `udsota_init` does both. The host build checks that the core's `server/` compiles and links without the updater and includes none of its headers but that one, and that neither component's `server/` touches the updater's state or names an updater header directly; the port's `server/` still takes the updater through the umbrella `udsota.h`. On the ESP32 example (esp32 and esp32s3; default, compression and delta) the image grows by 484 to 536 bytes, 451 to 455 of them in `libudsota.a`, and `s_srv` by 8 bytes of internal RAM, 364 to 372 (the service table pointer, and 4 bytes of padding from nesting `udsota_update_t`); `sizeof(udsota_server_t)` on a 64-bit host goes from 568 to 584.
- Internal: `fuzz_udsota_no_update` fuzzes the server with no update service, where 34, 36 and 37 must only ever answer 0x11, or 0x21 while an app routine runs.
- Internal: the fuzz harness's PASS line ends with `digest=`, a hash of every request it sends and every answer it gets, so a changed answer shows even where the counts do not.

## [0.8.0] - 2026-09-29

`udsota pack`, for updates that a flasher other than the client sends, and a README that walks through using udsota and managing its keys.
- Client: `udsota pack FILE --out DIR [--dfi XX]... [--diff-from BASE]` writes the payloads `flash` sends, byte for byte, for DFI 0x00, 0x10, and 0x20 and 0x30 from a base, with a JSON manifest of what a flasher needs to send them, for a flasher that is not this client, such as an edge device that gets its updates from a server (client README). It needs no bus. The core README's new "Flashing without the client" gives the sequence and its fallbacks.
- Fixed, client: a delta download whose 0x31 naming `DL_BAD_BASE` is lost now falls back to the full download, as when it arrives. The resent block, over 256 bytes, found the download ended and got no flow control, and `flash` stopped with exit 1.
- Docs: the README gains a how-to-use walk-through (integrate, profile, build, flash, pack), a step-by-step account of an update, and a key-management section: both keys, unlocking from an edge device without the private key, and rotation. It now says that rollback needs `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`, which ESP-IDF leaves off.

## [0.7.0] - 2026-09-29

A cleanup pass over the whole tree: two smaller adapter structs, a few fixes in the client and the demo server, and a wider CI build. Nothing changes on the wire.
- **Breaking**, core: `udsota_isotp_t` and `udsota_rxwatch_t` change layout. The rxwatch sequence number and interval ring now follow from `cf_count`, and the isotp-c send buffer holds one answer (`UDSOTA_ISOTP_TX_MAX` = `UDSOTA_ISOTP_RESP_MAX`, 256 B, was 512 B), so `udsota_isotp_bufs_t` drops from 9,214 to 8,958 bytes. Callers that allocate with `sizeof` need no change.
- Core: `udsota_isotp_init` takes BS, the default STmin and the download receive limit from the server's resolved `s->cfg`, not the caller's raw cfg, so the ISO-TP receive limit is always the maxNumberOfBlockLength that 0x74 announces. `resp_id` and `fc_retry_ms` still come from its `cfg` argument.
- Fixed, client: a compressed `flash` whose RequestDownload gets NRC 0x22 reports that 0x22 even when F1F1 cannot be read afterwards; the failed F1F1 read's error hid it before.
- Client: a u8 or u16 `[dids]` entry stores its effective `min` and `max`, the type's bound where the profile gives none (0, and 255 or 65535), instead of `None`. The profile format and CLI output are unchanged.
- Fixed, `udsota_demo_server`: its temporary state directory (about 4 MB of slot files) is removed on every exit once made, including when opening or seeding the slots fails, and a `--state-dir` too long for the fake's 240-byte path is refused with "cannot open the slots" instead of being cut to 239 characters.
- ESP32 port: the "no memory for DFI 0xNN's decoder" warning names the DFI and the largest free internal block and drops its byte total, which left out the delta decoder. `udsota_esp32.h` now says `abort` does nothing before start (it returns no error), and lists everything that takes the PSA lock. The boot-time OTA state read runs before the worker's first job instead of as a queued job, so it no longer takes a queue slot; `udsota_esp32_engine_busy()` is true until it has finished. This one has not yet run on hardware.
- CI also builds the ESP32 example with compression but not delta (`sdkconfig.compression`) on esp32 and esp32s3, and its warning gate no longer depends on being the step's last line. `tools/run_tests.sh` runs ctest in parallel, and CI's host job calls it. RELEASING.md says the notes always come from `main`'s CHANGELOG, as the workflow already did.
- Internal: shared test harnesses and mocks, the codec tests pin reasons 12-15 and DFIs 0x10, 0x20 and 0x30, fuzz_udsota's coverage floor covers every served SID (0x28 and 0x85 included), and the READMEs are brought up to date for delta downloads, including the demo server's `--no-delta`.

## [0.6.0] - 2026-09-28

Delta downloads: a 34 with dataFormatIdentifier 0x20 or 0x30 carries a patch from the image the device runs, and the device rebuilds the new image from its running slot, so a small code change costs kilobytes on the bus instead of the whole image (for the example, a one-line change is 5,493 bytes under 0x20 and 1,027 under 0x30, against 192,794 compressed). 0x20 takes Espressif's `esp_delta_ota` patches as their own tool writes them; 0x30 is the same format with an uncompressed patch, all of it raw DEFLATE, which is usually several times smaller. The rebuilt image gets the same first-block check before any erase, FF01 verify, activate and confirm as a full one, and the running slot is only ever read. It is off unless the engine serves it; the ESP32 port leaves it off by default. It has run on the host, over the Linux demo server's frame pipe and in QEMU, but not yet on hardware or a real CAN bus.
- **Breaking**, core: `engine.zbegin` gains the DFI, `int (*zbegin)(void *ctx, uint32_t size, uint8_t dfi)`, and `udsota_engine_t` gains `uint16_t zformats` after `zwritten`, naming the coded DFIs the engine serves (`UDSOTA_DL_FMT(0x10) | ...`). An engine that served 0x10 must set `zformats = UDSOTA_DL_FMT(UDSOTA_DL_DFI_DEFLATE)`; with it 0, no coded DFI is served. A DFI the engine does not serve now answers 0x31 before anything changes, as an unknown one does. New reason 15 `UDSOTA_DL_BAD_BASE`: a patch made from another image than the running one, refused at the 36 with 0x31 before any erase; a full download still works. Reason 13 also covers a delta header with the wrong magic, a patch for another size, a read outside the running slot, and bytes after a patch's end, refused at the 36 that carries them. `engine.zend` may now return `UDSOTA_PENDING`, and the server answers the 37 with 0x78 until the job ends, as for a 36: a heatshrink patch's decoder can still hold the image's last bytes when the input ends, so its end can read and write flash. On the ESP32 port every coded 37 now runs on the flash worker, so a 0x10 one can answer 0x78 too.
- Core: the rule that nothing is erased before the first block passes moves from the compressed stream into `udsota_isink.h`, which the stream and the new delta patch stage (`udsota_patch.h`, a `udsota_patch_t` decoder interface) both write through; `udsota_coded.h` chains the stages for a DFI, so an engine supplies only its sink, buffers and decoders. The image sink now writes the last of an image as soon as all of it is in. `udsota_zstream_t` keeps its API and results, but its image fields (`written`, `held`, `size`, `begun`) move into its `image` member, and `udsota_zsink_t` into `udsota_isink.h`; `udsota_zstream_open_push()` inflates into a next stage instead of an image.
- Fixed, `udsota_inflate`: the dictionary is cleared at each stream's start, so a back-reference before the stream's first byte, which tinfl allows and zlib refuses, copies zeros instead of stale heap bytes (for 0x10 downloads too).
- New component `udsota_delta`: a `udsota_patch_t` on detools 0.53.0's sequential patcher, vendored unpatched for heatshrink and uncompressed patches (THIRD_PARTY.md). Its state is 672 bytes on the ESP32-S3.
- ESP32 port: `CONFIG_UDSOTA_ESP32_DELTA` (default n, needs `CONFIG_UDSOTA_ESP32_COMPRESSION`). The worker reads the base with `esp_partition_read()` and refuses a read outside the running partition; a patch names its base by the running image's appended SHA-256, read with `esp_image_get_metadata()`. A 0x20 download holds about 4.8 KB of internal heap from its 34 to its 37 or abort, and a 0x30 one about 50 KB, 6 KB with `CONFIG_UDSOTA_ESP32_INFLATE_PSRAM`; nothing at boot. It adds about 4 KB to the example's image, and a build with compression but not delta links the core's patch stage (about 2 KB) but not detools. `examples/esp32/sdkconfig.delta` turns it on for the example.
- Client: `flash --diff-from PATH` offers a delta download, PATH being one base `.bin` or a directory of them; the tool uses the one carrying the device's running app_elf_sha256 (F1F3), builds the patch for each mode it may try, and tries those smaller than the full download, smallest first, then the full download. A 34 answering 0x31, or 0x22 with `DL_NO_MEMORY`, moves on to the next mode, and a 36 refused with `DL_BAD_BASE` (a re-signed build of the same source, for example) goes straight to the full download. `--diff-format auto|heatshrink|deflate` limits the modes, and `--no-compress` rules out 0x30. It needs the new optional extra `diff`, `pip install "./client[diff]"` from the repository (detools, which builds from source). The base must be the very `.bin` that was flashed. `--drop-76` is refused with `--diff-from`.
- The Linux demo server serves delta downloads (`--no-delta` turns them off), and new pipe end-to-end tests drive them. New host tests (`test_udsota_server_delta`) run the real decoder on fixtures from `tools/make_delta_fixtures.py`, whose 0x20 patch is byte for byte what Espressif's `esp_delta_ota_patch_gen.py` writes.

## [0.5.1] - 2026-09-28

Fixed: a refused download now exits 1 instead of hanging. When a server withheld its flow control mid-block and ignored the resent block, `udsota flash` over the kernel's ISO-TP socket could hang for ever after the failed resend. A block that fails after its resend now names the block, and after a send the server stopped also F1F1's reason, such as `block 1: ... F1F1 reads DL_ABORTED, 0 bytes received`. The demo server gains `--withhold-fc-after N` and `--drop-fc-after N` to inject both faults. Not breaking.

## [0.5.0] - 2026-09-28

The ESP32 port says which image is arriving: the new `udsota_esp32_incoming_version()` copies out the version from the image's `esp_app_desc_t`, so an update screen can say "Installing v0.3.1" and, after a failure, name the version next to `last_reason`. It is set when the first-block check accepts the image, compressed downloads included, kept after the download ends, and cleared by the next accepted 34 in the same locked copy as that 34's ERASING report, or by a compressed 34 refused for memory, so that refusal never names the previous image. A display that pairs the version with `last_reason` reads the progress, the version, then the progress again, and retries if they changed. It holds at most 31 characters, with non-printable bytes shown as `?`, and lives in RAM only. Additive and not breaking: the port gains one function and `UDSOTA_ESP32_VERSION_MAX`, and the core, its structs and the wire are unchanged.

Releasing is one step: **Actions → cut release**, with minor or patch, dates `[Unreleased]` as the next version, sets `__version__`, commits to `main`, tags it and publishes the Release. `tools/release.py bump` makes the two edits, for a release by hand. Nothing changes in the library or the client.

## [0.4.0] - 2026-09-28

Releases have a written process, [RELEASING.md](RELEASING.md): semantic versioning where, while udsota is 0.x, anything new or breaking is a minor bump and a patch is for fixes only; one version shared by the tag, the dated CHANGELOG heading and the client's `__version__`; and a release workflow that checks those agree, then publishes the client's wheel and the example's images as a GitHub Release. `tools/release.py` does the check and extracts the notes. 0.1.0 is dated and tagged: it is the initial import, `da16abf`.

Apps can show an update's progress. `udsota_progress()` reads the download's stage (IDLE, ERASING, WRITING, VERIFYING or ACTIVATING), the image bytes written of the size the 34 announced, and the last download's F1F1 reason, so a display can show a failure rather than just falling back to idle. The new optional `hooks.progress` gets the same at each change of stage and after each written block, at most once per server call, and `udsota_progress_permille()` turns the bytes into permille. The ESP32 port keeps the last report in a snapshot under a spinlock, which any task reads with the new `udsota_esp32_progress()`, and forwards the hook to the app's with its `ctx`.

Additive, with nothing changed on the wire: `udsota_hooks_t` gains `progress` after `routine_poll`, and `udsota_server_t` gains `dl_written`, `progress_stage` and `progress_block` at its end. With the hook NULL every answer is the same bytes, and a third fuzz build, `fuzz_udsota_progress`, sets the hook and checks that `done` never passes `total` or shrinks within a download.

Compressed downloads: a 34 with dataFormatIdentifier 0x10 carries the image as a raw DEFLATE stream, so an update spends about 40 % less time on the bus (the example image deflates to 61 %). memorySize stays the uncompressed size, and the device writes exactly the bytes an uncompressed download writes, so the image, its signature, the slot and every rule are unchanged. It is off unless the engine provides it; the ESP32 port and the client leave it off by default. It has run on the host, over the Linux demo server's frame pipe and in QEMU, but not yet on hardware or a real CAN bus.
- Core: `udsota_engine_t` gains `zbegin`, `zwrite`, `zend` and `zwritten`, appended after `ctx`. With `zbegin` NULL a 34 with DFI 0x10 answers 0x31 and every answer is as before. With them set, the server holds inflated bytes until the first-block check has 320 of them, and only then erases; a stream that does not inflate to exactly memorySize, or has data after its end, fails 37 with 0x72; a corrupt stream or one inflating past memorySize fails its 36 with 0x31. The compressed bytes are bounded by `UDSOTA_DL_Z_BOUND` (0x71 past it). New reason codes 13 `UDSOTA_DL_BAD_STREAM` and 14 `UDSOTA_DL_NO_MEMORY` (a 34 with no memory for the inflater answers 0x22). F1F1 counts compressed bytes for such a download, while progress counts image bytes: after each 76 the server takes the stream's count from the new optional `engine.zwritten`, and the 37 sets `done` to `total`. ERASING now ends when the first 36 is accepted rather than when the first bytes are written, the same moment for an uncompressed download, and the progress hook also runs when only `last_reason` changes (a compressed 34 refused for memory), which `udsota_server_t` tracks in a new `progress_reason`. `udsota_zstream.h` holds the decompressor interface (`udsota_inflate_t`) and the stream an engine runs behind the ops. Building `udsota_server.c` with `UDSOTA_COMPRESSION` 0 compiles all of this out of the server, which then answers DFI 0x10 with 0x31 whatever the engine sets. F000 answers FF after a compressed download too: compressed downloads cannot resume.
- New component `udsota_inflate`: a `udsota_inflate_t` on miniz's tinfl, the ROM's copy under ESP-IDF, which every v6.1 target has, else miniz 3.0.2, vendored unpatched (THIRD_PARTY.md).
- ESP32 port: `CONFIG_UDSOTA_ESP32_COMPRESSION` (default n); off, it also builds the core with `UDSOTA_COMPRESSION` 0, so an image without compressed downloads is within 32 bytes of one from before them (`-Os`). The flash worker inflates; the diag task only copies blocks. Each compressed download holds about 48 KB of internal heap from its 34 to its 37 or abort, or 4 KB with `CONFIG_UDSOTA_ESP32_INFLATE_PSRAM` (default y where SPIRAM is on, and not offered on an ESP32 below revision 3, whose PSRAM the ROM's tinfl must not write), and nothing at boot. `examples/esp32/sdkconfig.compression` turns it on for the example.
- Client: `flash --compress` sends the image compressed and prints the ratio and the time saved. A 0x31 to the compressed 34 (no compressed downloads, or an image larger than the slot) stops it with exit code 2, and a 0x22 with `DL_NO_MEMORY` with exit code 1; `--compress-auto` falls back to an uncompressed download on either, and `--no-compress` overrides the profile. `[image] compression` (`"none"`, `"deflate"` or `"auto"`) in a profile sets the default; a client before this release refuses a profile that uses it. Failures of a compressed 36 or 37 name F1F1's reason.
- The Linux demo server serves compressed downloads (`--no-compress` turns them off), and new pipe end-to-end tests drive them with frames and answers lost mid-stream. New host tests, and a fuzz variant (`fuzz_udsota_z`) with the decompressor installed that sends generated and mutated DEFLATE streams.

## [0.3.0] - 2026-09-28

Apps can serve their own writes and routines. WriteDataByIdentifier (0x2E) goes to a new `did_write` hook, and 31 01 on a RID the core doesn't own goes to a new `routine` hook. A routine may return `UDSOTA_PENDING` and finish in `routine_poll`, and the core treats it as a job meanwhile: 0x78, 0x21 to other requests, and the 90 s cap. Both hooks get a `udsota_access_t` with the session, the unlocked level and a session epoch, so the app decides which session and key each write needs and can drop state an earlier session left. The ESP32 port forwards all three hooks with the app's `ctx`.

Additive: `udsota_hooks_t` gains `did_write`, `routine` and `routine_poll` after `ctx`. With them NULL, 2E answers 0x11 and an unknown RID 0x31, as before.

The client gains `config show` and `config set NAME=VALUE ... [--commit] [--reset]`. A `[dids]` entry can be a typed, writable key (`type`, `writable`, `min`, `max`), and `u8` and `u16` decode as decimal. A `[config]` table names the commit routine, a status DID and an optional config-hash check. A client before 0.3.0 refuses a profile that uses them.

An ECDSA mode for SecurityAccess, after SAE paper 2022-01-0132, recommended for production. The device holds only the tester's P-256 public key, and the key in 27 02 or 27 04 is a 64-byte signature (r ‖ s) over SHA-256("udsota-27-ecdsa-v1" ‖ seed ‖ level ‖ id_len ‖ device ID). No image or flash dump then unlocks any device, where the HMAC mode's fleet master key, built into every image, unlocks all of them. The HMAC mode stays the default, and its keys and wire are unchanged.
- Core: `udsota_security_t` gains `verify` and `key_len`, appended after `ctx`. With `verify` set, the server asks it instead of computing the key, and a sendKey must be exactly 2 + `key_len` bytes. Counting, lockout, single use, expiry and NRC order are as before. `udsota_keys_sig_msg()` builds the signed message, and `udsota_keys_sig_self_test()` checks a verify against a published test key.
- ESP32 port: `cfg.key_pubkey` and `cfg.key_pubkey_len` (appended to `udsota_config_t`) turn security on in the ECDSA mode through the new `udsota_esp32_security_ecdsa()`. It verifies with PSA ECDSA under a public key imported once, after a start-up self-test. `key_pubkey` wins over `key_label`, and a `key_master` given with it is ignored with a warning.
- Client: `[security] mode = "ecdsa"` with `private_key_file` (or `--private-key`) signs each seed, and `udsota keygen --out DIR` writes `udsota_private.pem` and `udsota_pubkey.h`. The client now depends on cryptography (42 or newer).

Added:
- Functional addressing: `cfg.func_id` and `udsota_isotp_on_func_frame()`. A single frame on that ID is served when it is 10 01, 10 03, 3E, 22, 28 or 85, with NRCs 0x11, 0x12, 0x31, 0x7E and 0x7F suppressed; anything else, and anything during a flash job but 3E, gets no answer. The ESP32 port routes the ID, and the example listens on 0x7DF.
- 28 CommunicationControl through the new `hooks.comm_control` and 85 ControlDTCSetting through the new `hooks.dtc_setting`. Without its hook each still answers 0x11, as before. A return to the default session undoes both.
- `cfg.p2_prog_ms` and `cfg.p2star_prog_ms`: P2 and P2* for the programming session, carried by its 10 02 answer and followed by its 0x78 cadence.
- The client's optional `[functional]` table: the functional ID, and `quiet_bus`, which quiets every node on the bus (10 83, 85 82, 28 83 03, then 3E 80 every 2 s) while `flash` runs and releases them afterwards.
- The ESP32 port's flash worker wakes the diag task as each job finishes, so a block's 76 leaves as soon as its write is done.

Fixed:
- Core: `udsota_init()` now returns `bool`, false for a `security` with no `rng16` or with neither `key` nor `verify`. Such a server keeps security on and answers 0x22 to every requestSeed (no `rng16`) or sendKey (no `key` or `verify`), so nothing unlocks; before, the first requestSeed or sendKey called a NULL function. Code that ignores the result compiles unchanged.
- ISO-TP: the STmin sent in the flow control is rounded up to a value the FC can carry (100–900 µs in 100 µs steps, else whole ms up to 127 ms), and the STmin monitor judges that value. Before, isotp-c rounded down (950 µs went out as 0) while the monitor used the raw value, so an unencodable STmin could stop a client that honoured the FC exactly.
- ISO-TP: an answer the bus keeps refusing is dropped after 1 s (`UDSOTA_ISOTP_PARK_MAX_MS`, counted as lost). Before, it stayed parked and the server's poll, S3 included, never ran, so a bus with no acknowledging node could hold an unlocked session open.
- ISO-TP: with no `can.tx_pending`, a restart waits the full 100 ms for its answer to leave, as documented. Before, it fired at the next poll and the answer to ActivateImage or 11 01 could be lost in the driver's queue.
- ESP32 port: a wait under one FreeRTOS tick no longer becomes a non-blocking poll. At `CONFIG_FREERTOS_HZ=100` the diag task spun while a flash job ran and starved the flash worker on its core, so the first erase never finished. The port warns when the tick rate is under 1000 Hz, and the example sets 1000.
- ESP32 port: `udsota_esp32_on_frame()` clamps a DLC over 8 to 8.
- Client: no answer to ActivateImage no longer fails `flash`. The client reads F1F3 and F1F0: a server that answers nothing is restarting, one whose F1F3 is the new image has already restarted, and one whose boot slot switched restarts next, so in each case it waits for the new image and confirms it; one that runs the old image and has not switched never got the request, which is sent once more.
- Client: after NRC 0x21 the client listens out its backoff instead of sleeping through it, so when an earlier send's 0x78 was lost it takes the next 0x78 and waits for that request's answer. Before, a lost 0x78 on a job over about 3 s (an erase) ended the update with 0x21.
- Client: a 76 carrying the previous block's counter (a late answer to a resend) is passed over and the block's own answer awaited. Before, it ended the update with "block N answered with counter N-1".

Breaking, for code that fills `udsota_hooks_t` or `udsota_config_t` positionally: both gained fields (`comm_control`, `dtc_setting`; `func_id`, `p2_prog_ms`, `p2star_prog_ms`). Designated initializers are unaffected.

Breaking, in the ESP32 port only: `udsota_esp32_start()` also returns `ESP_ERR_INVALID_ARG` for a set `cfg.key_pubkey` that is not a 65-byte uncompressed point.

`tools/linux_server` is a Linux demo server for testing the client end to end. It runs the core's UDS server and ISO-TP adapter over SocketCAN or a stdin/stdout frame pipe. Its engine keeps two file-backed A/B slots, runs the real first-block rules and checks a real SHA-256 in FF01. It emulates rollback with an in-process restart after ActivateImage or 11 01, and security with `udsota_keys.c` over a host HMAC-SHA256. New client tests drive it: `client/tests/test_e2e_pipe.py` runs `cli.main` and `update` over the pipe with can-isotp's Python ISO-TP stack, and `client/tests/test_e2e_vcan.py` runs the `udsota` command on vcan0. A new CI job, `e2e`, builds the demo and runs the pipe tests, then the vcan tests where the runner can load vcan and can-isotp (they skip where it cannot). The three client bugs the pipe tests found are listed under Fixed. `--socketcan` accepts only a vcan interface unless `--allow-real-bus` is given, and the vcan tests skip unless `UDSOTA_VCAN` names one.

## [0.2.0] - 2026-09-28

The ESP32 port now derives the 0x27 keys from `cfg.device_id` when it is set (1 to 16 bytes), otherwise from the base MAC, so an app with its own device ID can unlock. Before, it always hashed the base MAC while F18C served the app's ID, and every key was refused (0x35, then 0x36 and 0x37). With `cfg.device_id` NULL, F18C and the keys are unchanged.

Breaking, in the ESP32 port only:
- `udsota_esp32_security()` takes the device ID: `(label, master, master_len, id, id_len)`, where `id` NULL means the base MAC.
- `udsota_esp32_device_id()` takes a `size_t *len` and returns the ID in use, not always the base MAC.
- `udsota_esp32_start()` returns `ESP_ERR_INVALID_ARG` for a set `cfg.device_id` whose length is not 1 to 16, and serves a copy of the ID as F18C rather than the app's buffer.

## [0.1.0] - 2026-09-27

First standalone release. udsota was developed and bench-tested inside a CAN-connected product before it was extracted here.

- The portable C11 core: UDS server (sessions, SecurityAccess, RequestDownload/TransferData/TransferExit, routines, DIDs), the ISO-TP adapter over isotp-c, image rules, key derivation and boot-loop logic.
- The ESP-IDF port: an update engine on `esp_ota_*` with A/B slots and rollback, PSA-based keys, the diag task and flash worker, and the image-descriptor macro and CMake helper.
- The Python client `udsota`, driven by TOML profiles, with an example profile.
- A minimal ESP-IDF example project, host unit tests with a request-parser fuzz harness, and CI.
