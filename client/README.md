# udsota client

`udsota` is udsota's PC client, unchanged since v0.14.2 but for one delta fallback (below). It reads a device's identity, update state and fault codes and installs firmware over UDS on ISO-TP, on Linux with SocketCAN and the kernel's ISO-TP module. Its reference (every command, the profile's tables and the exit codes) is [the client README at v0.14.2](https://github.com/ramb0t/udsota/blob/v0.14.2/client/README.md); this page covers only what is different against this repo's server.

```sh
pip install ./client                                  # Python 3.11 or newer; the udsota command
udsota --profile my.toml info                         # identity and update state
udsota --profile my.toml flash --compress app.bin     # precheck, download, verify, activate, confirm
```

From 0.15 udsota answers inside the app's iso14229 server, which the client handles. Outside the default session it sends `3E 00` before any request or 0x21 retry that comes over 2 s after the last `10` or `3E`, and a `3E` that gets no answer doesn't fail the request after it. It takes iso14229's 2-byte zero seed as already unlocked. It waits up to 2 s for the answer to a signed key. Two things work differently from udsota 0.14's own server, which the client still updates. A lost answer to a `36` or `37` fails the run instead of being recovered, so run `flash` again. And delta downloads come only as DFI 0x30, from a unit built with `UDSOTA_DELTA=1` and `cfg.allow_delta` set: `flash --diff-from` tries each delta smaller than the full download, smallest first, and a 34 answered 0x31, as 0x20 always is and 0x30 is on any other unit, moves on to the next, the full image last; of the payloads `pack --diff-from` writes, only 0x30's can be taken. A 36 refused with DL_BAD_BASE (a base other than the image the unit runs) still sends the full image next. When that refusal's answer is lost, the resent block gets 0x70 here, where a 0.14 server answered 0x24, and the client takes it the same way when F1F1 reads DL_BAD_BASE; if S3 has ended the programming session meanwhile, it enters that session and unlocks again first.

## Wire contract

`tests/test_udsota.py` checks the client's wire numbers against two contracts. Against `udsota_wire.h`, the wire contract `udsota.h` includes, with the NRCs and sessions it takes from `iso14229.h`, the numbers in `udsota/wire.py`, `keys.py` and `image.py` and the profile's default levels must match what this server answers. Against v0.14.2's wire headers, frozen in `test/fixtures/wire-v0.14/`, `wire.py`'s must match what units still on a v0.14.x server answer, so the client keeps updating those, and the block's few numbers the client never uses (F000 and its status, the seed lifetime, the DEFLATE overrun bound) must match them too. A number changed on either side fails the test, and so does a new `udsota_wire.h` number the test doesn't map.

## Bare images

A profile whose `[image]` sets `format = "bare"` takes images that are not ESP-IDF apps, such as a non-ESP unit's that speaks udsota's wire. It must also set `header_offset`, where the image file holds udsota's 224-byte bare header ([wire reference](../docs/wire.md#image-descriptor)). `udsota --profile my.toml stamp app.bin` stamps the build's output in place, or writes it to `--out OUT`: it pads the file and fills in the header's length, image ID and CRC, then checks the result against the profile as `flash` would, and leaves the file as it was if anything fails. A post-build script can call `udsota.image.stamp(data, header_offset)` instead, which needs no profile. `flash` and `pack` refuse an image whose length, CRC or image ID does not match, then check its descriptor as they check an ESP-IDF image's, with `desc_version` 1 or later. Plain and compressed downloads and `pack` work as for ESP-IDF images, with the image ID as the manifest's `image_elf_sha256`. Delta downloads need ESP-IDF's appended SHA-256, so `--diff-from` and DFI 0x20 and 0x30 are refused. The default, `format = "esp-idf"`, refuses `header_offset`, and `stamp` refuses that profile.

## Bootloader flow

A profile whose `[update]` sets `flow = "bootloader"` updates a single-slot unit whose resident bootloader is its only UDS server ([wire reference](../docs/wire.md#bootloader-flow)). `flash` first reads F1F4 once, and stops there with nothing to do if the app already runs the image and reports healthy. Otherwise it sends `10 02`, which resets the app into the bootloader, makes the precheck and the download there, waits 3 s for the restart, then polls F1F4 until the new app reports healthy with the image ID's first 4 bytes, for up to `start_timeout_s` more (1 to 600, default 60). It fails if the app runs another image, if the bootloader answers instead because the app did not start, or if nothing answers in time. For a unit whose app runs but cannot hand over, `flash --wait-for-unit SECONDS` (1 to 600) also catches the bootloader's power-up window: when the first `10 02` is not answered, it says to power-cycle the unit and sends `10 02` again, each at most 50 ms after the last went unanswered, was refused or failed to send, until one is answered, then discards the answers to the others; it fails if none is answered within SECONDS of that prompt. Only the first `10 02` waits out a 0x78 and retries a 0x21 with backoff, as any request does; a later one waits no longer than 50 ms after either, and while nothing acknowledges the frame each send waits out the kernel's echo timeout, so a try then takes seconds. There is no ConfirmImage, so `confirm` is refused, and the app serves no UDS, so `config` and `dtc` are refused. `reset` sends `10 02`, the programming unlock and `11 01`, and `info` reads from the bootloader, which stays there until its session times out. The default, `flow = "app"`, refuses `start_timeout_s`.

## Tests

`python -m pytest client/tests` runs the unit tests, on virtual buses with no CAN interface, and the end-to-end tests. Without the `diff` extra the delta tests skip.

The end-to-end test, `tests/test_e2e_lite.py`, drives `udsota_lite_server` over a frame pipe, which can lose or delay any frame. It covers `info`, a secured flash plain and compressed, a wrong master, a download without the key, each first-block refusal with its F1F1 reason, an FF01 failure, corrupt and truncated streams, a confirm that outlasts S3 and a control run without the keepalive in which S3 ends the session, `config set`, a seed asked for while unlocked, and an unconfirmed image that rolls back. Through the pipe's faults it covers a resent block ending the transfer with 0x24, a lost flow control, a lost request frame and a lost ActivateImage answer. It also sends `pack`'s payloads as another flasher would and runs `dtc` against an app that serves no DTCs. Its delta cases run DFI 0x30 downloads: the whole sequence, a wrong base falling back to the full image, slow jobs, the fallback after a lost DL_BAD_BASE answer with the programming session entered again, and `pack`'s delta payloads from a wrong base, with and without that lost answer; under `--no-delta`, `--diff-from` falls back to the full image. These need the `diff` extra and, apart from the `--no-delta` case, a server built with `-DUDSOTA_DELTA=ON`. `$UDSOTA_LITE_SERVER` names the server; otherwise it is `build/udsota_lite_server`, which the top-level build makes. The test skips when that is not built, or when the `diff` extra or a delta build is missing, but with `$UDSOTA_LITE_SERVER` set, as CI sets it, a missing one fails instead.

`tests/test_e2e_lite_vcan.py` runs the same server on vcan0 (or `$UDSOTA_VCAN`, which must name a vcan) through its CAN_RAW socket: a keyed flash and a DFI 0x30 delta download over the Python ISO-TP stack and, where the kernel has can-isotp, the `udsota` command's flash and `info` and its recovery from a lost flow control. It also checks the server refuses `--can lo`, which needs no vcan. Each test skips when its vcan, server, kernel ISO-TP, `diff` extra or delta build is missing; with `$UDSOTA_VCAN` set, as CI sets it, a missing vcan, server, `diff` extra or delta build fails instead.
